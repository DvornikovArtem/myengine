# B4: оффскрин рендер-тест с эталонной картинкой на WARP

## Зачем это нужно

Правки рендера ломают картинку тихо: рефлексия шейдеров, материалы по именам ([B1](b1-material-params.md)), root signature, порядок слотов текстур, запись констант в буфер. Ни одно из этих мест не падает с ошибкой, если, например, вторая текстура попала в слот первой или `Float4` записался с переставленными компонентами: сцена просто выглядит иначе. Тесты без GPU такого не видят.

Тест `render_reference` рисует фиксированную сцену в render target и сравнивает результат с эталонной картинкой. Если картинка изменилась, тест падает, называет число отличающихся пикселей и сохраняет картинку с разницей. Это допфича задачи B4 (раздел 4 [architecture.md](architecture.md)); поведение движка она не меняет.

Заодно в панели Statistics появилась группа «Shaders» со счётчиками программ: см. раздел «Счётчики шейдеров в Statistics».

## Что рисуется

Сцена собрана в `Scene` ([RenderReferenceTests.cpp](../../tests/render/RenderReferenceTests.cpp)). Файлов проекта в картинке нет, кроме шейдера `assets/shaders/textured_lit`: текстуры (BMP) тест делает сам, материалы пишет во временную папку, шейдеры копирует туда же.

| Параметр | Значение |
| --- | --- |
| Render target | 256 x 256 |
| Камера | вид единичный; проекция оставляет x и y и переводит z в диапазон глубины (функция `Projection`) |
| Свет | `SetTargetLighting` с направлением (0.35, -0.55, 0.75) и ambient 0.3 |
| Цвет очистки | (0.08, 0.1, 0.14) |

Три объекта:

| Объект | Материал | Что проверяет |
| --- | --- | --- |
| Слева сфера (радиус 1 в модели, масштаб 0.46, сдвиг (-0.42, 0.28)) | `old`: старые ключи `texture` и `tint` на настоящем шейдере проекта `assets/shaders/textured_lit` (копия во временной папке) | Путь с освещением; перевод старых ключей: `texture` - первая текстура шейдера, `tint` - `gColor` |
| Справа вверху квад | `named`: шейдер `tests/render/shaders/material_probe.*`, текстуры по имени (`gTexture` - шахматка 8x8 оранжевая/кремовая, `gTexture2` - градиент 4x4), константы `gColor`, `gMix` 0.5, `gBoost` 0.05 | Вторая текстура в своём слоте по имени, запись констант по смещениям из layout |
| Внизу квад | `stub`: вторая текстура не задана (белая заглушка), `gMix` 1 | Виден только цвет `gColor`: проверяется белая заглушка и запись `gColor` |

Перед сравнением `CheckThePictureHasTheObjects` проверяет, что в центрах трёх объектов не цвет очистки. Это защита от эталона, снятого со сломанной картинки: пустой кадр иначе стал бы "правильным" эталоном и ничего бы не проверял.

## Почему WARP

WARP - программный адаптер DX12. Он растеризует одинаково на любой машине, а у видеокарт и драйверов фильтрация, округления и края треугольников разные. Один эталон на все машины возможен только на WARP.

- Включение: переменная окружения `MYENGINE_DX12_WARP=1`. `Dx12RenderAdapter` читает её при создании устройства, пропускает перебор аппаратных адаптеров и берёт WARP. Тест ставит её сам и проверяет, что имя адаптера содержит `WARP`; иначе падает с понятным сообщением.
- Отладочный слой тест не включает.
- Если WARP недоступен или нет рабочего стола для скрытого окна, тест завершается кодом 77 и CTest показывает `Skipped`; причина печатается.

## Допуск

Канал может отличаться не больше чем на 2 из 255 (`kChannelTolerance`). Не больше 0.1 % пикселей (`kPixelFractionTolerance`, 65 из 65536) могут отличаться сильнее.

Почему так. WARP детерминирован на одной версии Windows: в прогонах Debug и RelWithDebInfo отличается 0 пикселей, максимальная разница канала 0. Но `d3d10warp.dll` обновляется вместе с Windows, и новая версия может иначе округлить фильтрацию текстуры или деление, а край треугольника может сдвинуться на пиксель. Допуск рассчитан на такой шум.

Реальные поломки меняют тысячи пикселей. Это проверено порчей кода:

| Порча | Пикселей отличается | Максимальная разница канала |
| --- | --- | --- |
| При записи `Float4` переставлены компоненты y и z | 25243 | 89 |
| Все слоты текстур берут первую текстуру | 14393 | 227 |
| Не записывается `tint` материала | 10850 | 62 |

Допуск в 65 пикселей в сотни раз меньше любой из этих поломок.

## Что делать при провале

Тест печатает, сколько пикселей отличается, сколько из них сверх допуска и максимальную разницу канала. Затем сохраняет в `build/render_reference/` две картинки и печатает их пути:

- `actual.png` - что нарисовано сейчас;
- `diff.png` - чёрное: совпало; красное: отличается; пурпурное: отличается сверх допуска.

Пурпурная область показывает, какой объект сломан:

| Где пурпурное | Что подозревать |
| --- | --- |
| Сфера | Свет, перевод старых ключей `texture` и `tint`, путь шейдера `textured_lit` |
| Верхний квад | Вторая текстура по имени, константы по именам |
| Нижний квад | Белая заглушка для незаданной текстуры, `gColor` |
| Всё сразу | Общая часть: камера, root signature, очистка, запись `Float4` |

Дальше: если изменение картинки не задумано, искать ошибку в последней правке. Если задумано (например, поменяли освещение), обновить эталон.

## Как обновить эталон

Только намеренно:

```text
build\tests\Debug\myengine_render_reference_tests.exe --update-reference
```

Вместо флага можно задать переменную `MYENGINE_UPDATE_REFERENCE=1`. Тест перезапишет [scene_256.png](../../tests/render/reference/scene_256.png) и напечатает путь. Обычный прогон эталон никогда не перезаписывает.

Перед коммитом новую картинку нужно посмотреть глазами. PNG коммитится отдельным коммитом с объяснением, почему картинка изменилась. PNG пишется и читается через DirectXTex/WIC (`SaveToWICFile`, `LoadFromWICFile`).

## Счётчики шейдеров в Statistics

Панель Statistics получила группу «Shaders», оформленную так же, как остальные (`DrawStatsGroup`):

| Строка | Что показывает |
| --- | --- |
| Programs | Число программ шейдеров |
| Pipeline states | Число PSO |
| Root signatures | Число root signatures |
| Reloads | Перезагрузки в виде «N ok / M failed» |

Данные приходят через `ShaderStatusView` (поля `programCount`, `pipelineStates`, `rootSignatures`, `reloads`, `reloadFailures`, `available`), заполняет их `Application.cpp` из `GetShaderStatistics` адаптера. Если рендерер чисел не дал (`available` равно `false`), группа не рисуется. Окно `Help -> Developer -> Shader Layouts` осталось и показывает те же числа строкой, плюс объекты, которые ждут GPU.

Группа нужна для живых сценариев 3 и 13 протокола [stability.md](../measurements/lab3/stability.md): при перезагрузках шейдера эти числа не должны расти.

## Как запустить

```text
ctest --test-dir build -C Debug -R render_reference --output-on-failure
```

Время около 0.3 с в Debug и 0.6 с в RelWithDebInfo. Таймаут в CTest 180 с.

## Ограничения

- Эталон проверяет только картинку одной фиксированной сцены на WARP.
- Аппаратные адаптеры он не проверяет: это делают `render_stability` и `material_render`.
- UI тест не проверяет, в том числе новую группу «Shaders».
- Эталон привязан к WARP: если в новой версии Windows картинка уйдёт за допуск без правок кода, эталон придётся обновить по правилам выше. Такого случая пока не наблюдали: эталон снят на Windows 11, в Debug и в RelWithDebInfo картинка совпала с ним попиксельно.
