# Поиск ошибок в C++: ASan, /analyze, clang-tidy

Три проверки, которые ловят то, что компилятор и тесты не видят: выход за границы, обращение к освобождённой памяти,
утечки, неинициализированные значения, забытые проверки результата. Всё запускается одним скриптом
`tools\check.ps1`; обычные сборки `Debug` и `RelWithDebInfo` от этих проверок не меняются — у каждой проверки своя
папка сборки.

## Быстрый старт

```powershell
powershell -File tools\check.ps1            # = -Quick: Debug-сборка в build/ и ctest
powershell -File tools\check.ps1 -Asan      # build-asan/: ctest + смоуки + короткий прогон редактора
powershell -File tools\check.ps1 -Analyze   # build-analyze/: MSVC /analyze, сравнение с baseline
powershell -File tools\check.ps1 -Tidy      # build-tidy/: clang-tidy, сравнение с baseline
powershell -File tools\check.ps1 -All       # всё вместе (десятки минут)
```

Скрипт печатает по строке на шаг (`OK` / `FAIL`), число найденных замечаний в нашем коде и путь к логу. Полные логи —
в `<папка сборки>\logs\`. Код возврата `0` — всё зелёное, `1` — что-то упало или появились новые замечания. Скрипт
работает из папки с кириллицей в пути (ASCII-only, процессы запускаются через .NET `Process`).

Когда что запускать:

| Правка | Что прогнать |
| --- | --- |
| любая задача | `-Quick` |
| память, указатели, контейнеры, время жизни, потоки, загрузка ресурсов | `-Asan` |
| новый модуль, крупный рефакторинг | `-Analyze`, `-Tidy` |
| перед мержем большой серии | `-All` |

## AddressSanitizer (`-Asan`)

CMake-опция `MYENGINE_ASAN=ON` (только MSVC, только в своей папке `build-asan/`) собирает **наши** цели
(`engine/`, `app/`, `tests/`) с `/fsanitize=address`. Что при этом происходит:

- В `Debug` убираются `/RTC1` и `/ZI` (ASan с ними не работает), для исполняемых файлов — `/INCREMENTAL:NO`.
- Рядом с каждым `.exe` лежат `clang_rt.asan_dbg_dynamic-x86_64.dll` и `clang_rt.asan_dynamic-x86_64.dll`
  (копируются из папки компилятора отдельной целью CMake, как рантайм-ассеты).
- Заданы `_DISABLE_VECTOR_ANNOTATION` и `_DISABLE_STRING_ANNOTATION`: готовые `DirectXTK12` и `DirectXTex` собраны без
  ASan, и аннотации контейнеров дают ошибку линковки `LNK2038`.
- Сторонний код (ImGui, pybind11, DirectXTK и т. д.) не инструментируется; его ошибки в отчёт не попадают.
- Под ASan всё медленнее примерно в 10 раз: таймауты тестов в `tests/CMakeLists.txt` умножаются на 10, лимит
  времени кадра в тесте ассистента поднят (макрос `MYENGINE_ASAN_BUILD`).

Шаги скрипта: сборка `build-asan/`, `ctest`, `myengine_gameplay_smoke`, `myengine_scripting_smoke` и короткий прогон
редактора `myengine.exe --scene <копия coin_guard_demo> --play --exit-after-frames 300` (число кадров — параметр
`-AsanFrames`). Копия сцены нужна, потому что редактор при выходе записывает карту обратно.

Вывод программы — `build-asan\logs\asan-<шаг>.log`, отчёты ASan — `asan-<шаг>-report.<pid>` там же (опция
`log_path`; путь с буквой диска в `ASAN_OPTIONS` обязательно в кавычках). Любой отчёт — провал шага.

### `--exit-after-frames <n>`

Ключ редактора `myengine.exe`: завершить главный цикл после `n` кадров с кодом `0`. Нужен для коротких прогонов под
санитайзером и профайлером; без ключа поведение не меняется.

### Что делать с найденным

1. Ошибка в нашем коде — чинится в коде, регрессионный тест — если есть куда его положить.
2. Ошибка в чужом коде — подавление с комментарием «что и почему» рядом с подавлением (чужие библиотеки и так не
   инструментированы, поэтому нужно оно редко).
3. Подавлять нашу ошибку «потому что медленно» нельзя.

## MSVC `/analyze` (`-Analyze`)

Опция `MYENGINE_ANALYZE=ON` включает `/analyze /analyze:external-` для наших целей (заголовки зависимостей подключены
как `SYSTEM`, их не анализируем). Сборка — в `build-analyze/`, лог — `build-analyze\logs\analyze-build.log`.
Скрипт отбирает предупреждения `C6xxx` / `C28xxx` только из файлов `engine/`, `app/`, `tests/`.

## clang-tidy (`-Tidy`)

`compile_commands.json` делает генератор Ninja внутри окружения `VsDevCmd` (в папке `build-tidy/`; у генератора
Visual Studio базы компиляции нет). Скрипт сам настраивает эту папку, запускает `clang-tidy` из VS (`VC\Tools\Llvm`) в
8 процессов на наших `.cpp` и разбирает вывод. Набор проверок — в `.clang-tidy` в корне, умеренный: `bugprone-*`,
`performance-*` и несколько точечных. В файле перечислено, что и почему выключено.

Если `clang-tidy` не смог обработать файлы (неверный вызов, нет базы), шаг падает с `FAIL`, а не печатает «0 замечаний».

## Baseline

Что осталось в коде и признано шумом (ложные срабатывания, намеренные приёмы), записано в
`tools/baselines/analyze.txt` и `tools/baselines/tidy.txt` в формате `проверка|файл|количество`. Шаг падает только
если количество замечаний в каком-то файле **выросло** или появилась новая пара «проверка + файл». Сдвиг номеров
строк baseline не ломает.

- Новое замечание: сначала чиним. Ложное срабатывание — либо правим код так, чтобы оно ушло, либо в одном
  коммите с причиной обновляем baseline: `tools\check.ps1 -Tidy -UpdateBaseline` (аналогично `-Analyze`).
- Смотреть, что именно найдено: `build-tidy\logs\tidy-findings.txt`, `build-analyze\logs\analyze-findings.txt`.
- Baseline только уменьшается: после исправления запустите шаг с `-UpdateBaseline`, чтобы строки ушли.

## Если что-то не работает

- `LNK2038 annotate_vector` — какая-то цель собрана без `_DISABLE_VECTOR_ANNOTATION`; перенастройте `build-asan/`
  (`cmake -S . -B build-asan`: регенерация CMake в проекте отключена, после правок `CMakeLists.txt` нужен явный
  configure).
- `expected '=' in ASAN_OPTIONS` — путь с `C:\` в `ASAN_OPTIONS` не взят в кавычки.
- ASan-тест упал по таймауту, хотя без ASan проходит — проверьте, что тест получил множитель ×10 (раздел в
  `tests/CMakeLists.txt` в конце файла) и что запущен именно `build-asan`.
- Мало места на диске: каждая из трёх папок сборки занимает 1–2 ГБ. После работы удаляйте `build-asan/`,
  `build-analyze/`, `build-tidy/` (основную `build/` не трогаем).
