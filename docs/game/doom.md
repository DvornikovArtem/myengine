# FlyDoom: классический DOOM в движке (D0)

Настоящий DOOM 1993 года (исходный код id Software 1997 года через порт doomgeneric) как отдельная игра на движке: кадр игры рисуется текстурой DX12 на всё окно, клавиатура и мышь идут в игру, звук и музыка — через наш `AudioSystem`. Сам DOOM не переписан: логика, карты, враги, оружие и демо работают 1:1, поэтому демо-записи id проигрываются кадр в кадр. Игра нужна как «тело» для следующих задач серии FLYDOOM: мозг мухи и мухи-противники (N1, D1) управляют игроком через команды такта.

## Быстрый старт

```powershell
powershell -ExecutionPolicy Bypass -File tools\doom\fetch_freedoom.ps1   # один раз: Freedoom -> assets\doom\freedoom1.wad
.\build.bat RelWithDebInfo FlyDoom                                       # build\app\RelWithDebInfo\FlyDoom.exe
build\app\RelWithDebInfo\FlyDoom.exe                                     # или: myengine.exe --game doom
```

`FlyDoom.exe` — та же программа, что `myengine.exe`, с игрой, зафиксированной на DOOM (отдельная цель CMake `FlyDoom`, свои значок и свойства exe; файлы пользователя лежат в `%LOCALAPPDATA%\FlyDoom`). `myengine.exe --game doom` делает то же самое из редактора. `myengine.exe --game` без `doom` по-прежнему открывает Rocket Arena, сама игра и редактор не затронуты.

Аргументы командной строки (общие для обоих exe):

| Аргумент | Что |
| --- | --- |
| `--iwad <файл.wad>` | какие игровые данные взять (иначе поиск, см. ниже) |
| `--doom-args "<строка>"` | командная строка самого DOOM как есть: `"-warp 1 1 -skill 3"`, `"-playdemo demo1"`, `"-nomonsters"` |
| `--doom-square-pixels` | не растягивать кадр 320×200 до 4:3 (по умолчанию растягивается, как на мониторах 1993 года: пиксель DOOM был высоким) |
| `--doom-no-music` | без музыки (эффекты остаются) |

## Игровые данные (WAD)

DOOM — это движок плюс данные игры (WAD). Данные оригинала в репозиторий и в сборку не кладутся ни при каких условиях. Порядок поиска (`doom::FindIwad`):

Места, по порядку:

1. `--iwad <файл>`: то, что назвал игрок, берётся как есть; если файла нет, игра показывает ошибку, а не берёт другой;
2. `assets/doom/`, `wads/`, `doom/` или сама папка exe (`wads/` — куда пакет кладёт shareware `doom1.wad`);
3. папка WAD игрока `%LOCALAPPDATA%\FlyDoom\wads\` (и `<папка данных игры>\wads`, для `myengine.exe` это `%APPDATA%\myengine\wads`): сюда игрок кладёт свой WAD вне репозитория и вне пакета;
4. DOOM из библиотеки Steam игрока (реестр `Steam\SteamPath` и `libraryfolders.vdf`: `steamapps/common/Ultimate Doom/rerelease/DOOM.WAD`, `DOOM + DOOM II`, `Doom 2`, `Final Doom`, `Doom 3 BFG Edition` и подпапки `base`);
5. переменные окружения `DOOMWADDIR` / `DOOMWADPATH` (как у самого DOOM).

Из всего найденного выбирается по рангу: **полная игра** (`DOOM.WAD`, `DOOM2.WAD`, `plutonia.wad`, `tnt.wad`) выше **shareware** (`doom1.wad`, первый эпизод), а он выше **Freedoom**; при равном ранге решает порядок мест. Какой WAD выбран и откуда, пишется в журнал (`DOOM: the game data is ... (from ...)`, остальные найденные — строками `another WAD found`). Shareware `doom1.wad` (v1.9, 4 196 020 байт) — настоящая игра id Software, бесплатная для распространения целиком: в репозиторий он не кладётся, а в пакет FlyDoom для друзей едет вместе с текстом лицензии (раздел «Раздать друзьям»).

Остальные найденные файлы остаются в `IwadSearchResult::alternatives` — меню выбора (D1) предложит их. Если ничего не найдено, окно показывает, где искали и что сделать, а `Esc` закрывает игру.

**Freedoom** (https://freedoom.github.io, лицензия — модифицированная BSD, текст в `assets/doom/COPYING-freedoom.txt`) — свободная замена данных DOOM, её можно держать в сборке. `tools/doom/fetch_freedoom.ps1` скачивает релиз 0.13.0 с GitHub, сверяет SHA-256 (значение зашито в скрипте) и кладёт `freedoom1.wad` (Phase 1, замена эпизодов Ultimate DOOM), лицензию и список авторов в `assets/doom/`. Файлы в `assets/doom/` игнорируются git (`.gitignore`), в репозитории лежит только `assets/doom/README.txt`. Оригинальный DOOM.WAD версии «rerelease» (Kex, 2019+) в этом порту может вести себя не так, как классический: если игра с ним ведёт себя странно, укажите `--iwad` на Freedoom.

## Управление

| Что | Клавиши |
| --- | --- |
| Идти вперёд / назад | `W` `S` или `↑` `↓` |
| Поворот | `←` `→` или мышь (курсор прячется и держится в окне, пока идёт уровень) |
| Боковые шаги | `A` `D` |
| Огонь | `Ctrl` или левая кнопка мыши |
| Открыть, нажать | `Пробел` или `E` |
| Бег | `Shift` |
| Оружие | `1`…`7` |
| Меню | `Esc` (стрелки, `Enter`, `Y`/`N`; в меню буквы — буквы) |
| Карта | `Tab` |
| Размер экрана, яркость | `-` `=`, `F11`; остальные `F1`…`F12` как в DOOM |
| Выход | меню → Quit Game (`Y`), закрывает окно; игра, которая закончилась ошибкой, показывает её текст |

Мышь: поворот идёт по сырому вводу (`WM_INPUT`), поэтому не упирается в край экрана; движение мыши вперёд-назад (как в оригинале — ходьба) отключено. Окно шлёт движение каждый кадр (60–240 Гц), а такт игры — 35 раз в секунду, и DOOM берёт из мыши только последнее событие перед тактом (в `G_Responder` для `ev_mouse` `mousex` присваивается, а не прибавляется): раньше при 144 Гц до игры доходила четверть движения, поворот был «почти нулевой». Теперь `DoomGame::PostMouse` складывает движение всех вызовов между тактами и отдаёт DOOM одним событием перед тактом, так что доходит всё: единица сырого ввода — 8/65536 круга (≈0,044°), рывок на 4096 единиц — пол-оборота, множитель «Mouse turn» из SETTINGS умножает это.

### Проверка без человека

Окно FlyDoom можно снять без участия человека: `FlyDoom.exe --screenshot <файл.tga> --screenshot-frame N --exit-after-frames M` (общие ключи движка) на скрытом рабочем столе (`.team/tools/run_hidden_exe.ps1`). Клавиши, которые нельзя нажать на скрытом столе, задаёт переменная окружения `MYENGINE_DOOM_KEYS="40:esc,44:-esc"` (кадр:имя, `-имя` отпускает; имена `esc enter up down left right fire use y n`; кадры считает `DoomGameFlow`). Так сняты `.team/tasks/d0-evidence/menu.png` (главное меню) и `e1m1.png` (`--doom-args "-warp 1 1 -skill 3"`). Мышь на скрытом столе (где настоящая не двигается) задаёт `MYENGINE_DOOM_MOUSE="300:2000,400:250,401:250"` (кадр:сырое движение по X; кадры считаются как у `MYENGINE_DOOM_KEYS`); угол игрока после каждого такта, где он изменился, пишется в журнал строкой `DOOM mouse script: ...`.

## Устройство

```
FlyDoom.exe / myengine.exe --game doom
 └─ Application                        engine/src/core/Application.cpp: окно, кадр, WM_INPUT, курсор
     └─ DoomGameFlow                   engine/src/game/DoomGameFlow.cpp: кадр в текстуру, клавиши в DOOM, звук в AudioSystem
         └─ doom::DoomGame             game/doom/src/DoomGame.cpp: часы, клавиши, кадр, состояние, источник команд
             ├─ myengine_doomgeneric   game/doom/third_party/doomgeneric (C, GPL v2) + DoomBridge.c, DoomSound.c, opl_render.c
             └─ DoomMusic              game/doom/src/DoomMusic.cpp: рабочий поток, OPL → PCM
```

- **`myengine_doomgeneric`** — исходники DOOM как есть (с несколькими помеченными правками, см. `third_party/doomgeneric/README-myengine.md`), собираются как C с `/W0`: предупреждения третьей стороны отключены только в этой цели, остальной проект собирается с `/W4`. Заголовки DOOM определяют свои `boolean`, `true`, `false`, поэтому C++ их не видит: всё, что должно их видеть, лежит в `DoomBridge.c`, `DoomSound.c`, `opl_render.c`, а в C++ идёт через `DoomBridge.h` без типов DOOM.
- **`myengine_doom`** — C++ часть без DX12, ImGui и ECS: класс `doom::DoomGame` (`include/doom/DoomGame.h`), поиск WAD, музыка. Под него написан тест `doom_core` — он запускает DOOM без окна и без звука.
- **`DoomGameFlow`** — клей с движком: подключает игру в `UiManager::SetGameUi` (она занимает место редактора, как `RlGameFlow`), каждый кадр опрашивает клавиатуру, продвигает игру, кладёт кадр в текстуру и рисует.
- **Выход из DOOM без `exit()`.** Оригинал завершает процесс из `I_Quit` и `I_Error`. В порту оба вызывают `DG_Exit`, который делает `longjmp` обратно в `DoomGame` (`DoomBridge.c`): пункт меню Quit Game и фатальная ошибка DOOM (плохой WAD) возвращают управление хозяину, а не убивают редактор. Ошибка DOOM становится текстом `DoomGame::ErrorMessage()`.
- **Один DOOM на процесс.** Всё состояние DOOM — глобальные переменные, поэтому `DoomGame::Create` работает один раз за процесс; после Quit или ошибки новый запуск требует нового процесса (повторный `Create` возвращает понятную ошибку).

### Время

Часы DOOM виртуальные: `DoomGame::Advance(dt)` двигает их на `dt`, и когда набралась 1/35 секунды (такт DOOM), выполняется `doomgeneric_Tick()`. Длинный кадр даёт несколько тактов за раз (как у самого DOOM), но `DoomGameFlow` ограничивает шаг 0.25 с, чтобы остановка в отладчике не превращалась в пробег. `DG_SleepMs` двигает те же часы, а не засыпает: игра не блокирует поток, и тест, вызывающий `Advance(1.0 / 35)`, получает ровно один такт на вызов — поэтому хэш кадра воспроизводится.

### Кадр

DOOM рисует 320×200 (`DOOMGENERIC_RESX/RESY`) в 32-битный буфер `0x00RRGGBB`. `DoomGameFlow` каждый новый кадр превращает палитру в RGBA, увеличивает его целым множителем (до ×4, ближайшим соседом, при 4:3 строки растягиваются 6/5) и обновляет текстуру через `IRenderAdapter::UpdateTexture` (новый метод: меняет пиксели под тем же handle, размер может меняться; в DX12 — новый ресурс под тем же дескриптором). Картинка рисуется по центру окна целым множителем экрана, если он помещается, с чёрными полями; при окне меньше 320×240 уменьшается. Так пиксели остаются квадратными блоками без размытия. Текстура обновляется 35 раз в секунду, не на каждый кадр движка.

### Звук

`DoomSound.c` — модуль звуковых эффектов и музыки DOOM (`sound_module_t`, `music_module_t`):

- эффект из WAD (формат DMX: 8 бит, моно, обычно 11025 Гц) разбирается и один раз отдаётся хозяину как 16-битный моно звук; в движке это `AudioSystem::CreateSound`;
- громкость (0…127) и разнесение по каналам (`sep`, 0…254) приходят от самого DOOM (он считает их по расстоянию и углу до источника); `DoomGameFlow` играет звук с `PlayParams` на единичной окружности перед слушателем: направление даёт панораму, громкость — `volume`, затухание по расстоянию выключено, чтобы не считать его дважды;
- **ограничение Wwise.** Сборка с `MYENGINE_WWISE=ON` не умеет играть сырые звуки: `AudioSystem::CreateSound` и `Play` там ничего не делают (см. `docs/engine/wwise.md`). В такой сборке DOOM работает без эффектов и музыки, в лог один раз пишется предупреждение. Для звука FlyDoom используйте сборку на XAudio2 (по умолчанию).

### Музыка

В WAD музыка лежит в формате MUS. Он превращается в MIDI (`mus2mid` из DOOM), а MIDI проигрывается так же, как в оригинале: на микросхеме FM-синтеза OPL (AdLib, Sound Blaster) по инструментам из лампа `GENMIDI` самого WAD. Мы используем модуль OPL из Chocolate Doom (`i_oplmusic.c`, GPL v2) и эмуляцию чипа Nuked OPL3 (LGPL v2.1) — `game/doom/third_party/opl/README-myengine.md`. Драйвер под ними (`opl_render.c`) не в реальном времени: песня целиком рендерится в PCM (стерео, 49716 Гц, родная частота чипа) на рабочем потоке, каждые 1/35 с `DoomMusic::Update` проверяет, готова ли она, и отдаёт её хозяину, который играет её зацикленно на шине Music. Рендер занимает доли секунды-секунды; пока он идёт, предыдущая музыка уже остановлена, новая начинается с запаздыванием. Смена песни отменяет рендер той, что не дорендерилась.

## Тесты

`ctest --test-dir build -C RelWithDebInfo -R doom_core` (цель `myengine_doom_core_tests`, без окна, без звука). Нужен WAD: берётся `--wad`, переменная `FLYDOOM_WAD`, затем shareware `%LOCALAPPDATA%\FlyDoom\wads\doom1.wad`, затем `assets/doom/doom1.wad`, затем Freedoom `assets/doom/freedoom1.wad`; проверенные хэши кадра зашиты для двух файлов: shareware doom1.wad 1.9 и Freedoom 0.13.0; **без WAD тест пропускается** (код 77, `SKIP_RETURN_CODE`) — один раз выполните `tools/doom/fetch_freedoom.ps1`. DOOM нельзя запустить дважды в одном процессе, поэтому тест перезапускает сам себя на каждый сценарий (`--scenario <имя>`) и читает строки `RESULT ключ=значение` из вывода:

`ctest --test-dir build -C RelWithDebInfo -R doom_determinism` запускает отдельный headless-тест: два свежих CPU-процесса получают один и тот же seeded ticcmd и сравниваются по хэшу наблюдаемого состояния (`Info`, `PlayerState`, ticcmd) и 320×200 кадра на каждом из 2200 тиков (62,9 секунды). Первая несовпавшая строка печатается как `first divergence tic ... world ... frame ...`, поэтому расхождение симуляции и рендера не смешивается. Для ручного replay trace от `myengine_fly_learn_measure` можно задать `DOOM_DETERMINISM_TRACE=<trace>`; тест воспроизводит первые 2200 команд после тех же десяти начальных тиков Fly learns. В обычном CI переменная не нужна: используется встроенный фиксированный маршрут.

Для исторической проверки Fly learns два независимых CPU trace с одним seed на Freedoom (по 4200 тиков каждый) совпали построчно, включая команды, состояние игрока, frame hash и brain step. Replay одного такого trace в двух свежих DOOM-процессах также стабилен. Это снимает гипотезы о расхождении ticcmd/brain scheduling и обычного DOOM replay для данного набора данных, но не доказывает исправление старого отчёта и не является основанием для renderer tolerance или speculative-патча.

| --- | --- |

| `audio` | звук и музыка: эффекты разобраны из WAD и отданы хозяину, выстрел запускает звук, музыка E1M1 отрендерена эмуляцией OPL (≈131 с, 49716 Гц, ≈4 с рендера), зациклена, не тишина |

| `badwad` | файл, который не WAD: `Create` возвращает текст ошибки, а не вызывает `exit()`; повторный `Create` отказывает с объяснением |

## Лаборатория: меню FlyDoom (V1, FD-MENU)

При запуске `FlyDoom.exe` без аргументов перед игрой открывается меню — «препарат на столе лаборатории»: чёрный фон с еле видной сеткой в 48 px, метки углов кадра, тонкие линии и прямые углы вместо плашек. Два смысловых цвета: **красный DOOM** (действие, фокус, «ты») и **циан мозга** (всё, что относится к мухе: облако, данные мозга, подписи на нём); заголовок так и написан, `FLY` циан и `DOOM` красный. Два шрифта (оба SIL OFL 1.1): узкий плакатный гротеск **Big Shoulders Display** (Black и ExtraBold) для крупных слов и моноширинный **JetBrains Mono** (Regular и Bold) для данных и текста. На заднем плане медленно вращается облако мозга мухи (164 789 нейронов, [brain-view.md](../flybrain/brain-view.md)); меню ходит и клавишами (стрелки, Enter, Esc, Y / N в диалоге выхода), и геймпадом (подсказки внизу меняются на круглые глифы A, B и D-pad), и мышью (наведение переносит фокус, клик по ◂ ▸ и по сегменту меняет значение, слайдер тянется).

Меню собрано из компонентов `engine/src/game/DoomMenuWidgets.{h,cpp}` (пункт меню, строка режима, степпер, сегменты, слайдер, кнопка, тег, клавиша, подсказка, раздел, лист, сигнальный путь, циферблат, диалог выхода) поверх примитивов и модели фокуса UI-кита (`rlui::Frame::Item`, `paint::*`); виджеты Rocket Arena (`MenuButton`, `StepperRow`, `HintBar`) FlyDoom не использует. Кит ничего не потерял: он только научился брать шрифты из набора, который назвала игра (`rlui::SetFontSet`, [rl-ui.md](rl-ui.md)); Rocket Arena набор не меняет и остаётся на Exo 2. Файлы шрифтов лежат в `assets/fonts/bigshoulders/` и `assets/fonts/jetbrainsmono/` вместе с `OFL.txt`, их тексты попадают в пакет (`games/flydoom/game.json`, `THIRD_PARTY.txt`).

**Звуки меню — звуки самого DOOM.** Из выбранного WAD (`DoomMenuSounds`, `ReadWadLumps` и `DecodeDmxSound` в `DoomLevels.h`) читаются лампы DMX и регистрируются в `AudioSystem` один раз при выборе WAD: смена фокуса — `DSPSTOP` (курсор меню DOOM, не чаще раза в 50 мс), Enter — `DSPISTOL`, Esc — `DSSWTCHX`, смена значения — `DSSTNMOV` (не чаще раза в 60 мс), «нельзя» — `DSOOF`, START — `DSTELEPT`, пауза — `DSSWTCHN` / `DSSWTCHX`, выход — случайный из звуков смерти и боли DOOM. DOOM и Freedoom звучат по-разному. Нет игровых данных — меню молчит: своих звуков у него нет, лицензировать нечего. Громкость — громкость эффектов из настроек, умноженная на 0,7.

**Анимация.** Первый показ меню (≈ 1,4 с, любая клавиша, клик или кнопка геймпада обрывает его): метки углов вырастают из углов, верхняя строка печатается, `FLYDOOM` загорается по буквам с мерцанием лампы, пункты въезжают слева, подписи на облаке появляются одна за другой, счётчики бегут от нуля. Внутри меню красная планка фокуса плывёт к новому пункту за 120 мс, новый экран появляется с короткой вспышкой заголовка, при смене режима досье перекрёстно проявляется и узлы цепочки загораются слева направо. После возврата из игры (LABORATORY) и при вызове нужного экрана по имени входа нет. **Menu motion = REDUCED** убирает мерцание, сдвиги, печать и бегущие счётчики: экраны только проявляются по альфе за 120 мс, весь вход — за 300 мс.

START затемняет меню (≈ 0,5 с), создаёт игру с выбранным WAD, уровнем (`-warp`, `-skill`) и контроллером режима и открывает её из чёрного (≈ 0,5 с). Мозг за меню останавливается и освобождает видеокарту до того, как игра создаст свой.

**Настройки** лежат в `%LOCALAPPDATA%\FlyDoom\settings.json` (JSON; кроме громкости, окна и мыши в нём `menuMotion` — 0 FULL / 1 REDUCED, `flies` — число мух роя 8…32, а для строк N4 `learnSpeed` — 1 (реальное время) или 0 (MAX: столько, сколько тянет мозг), `learnStart` — `scratch` или `trained` и `flyBrain` — `trained` или `scratch`; чувствительность мыши `mouseSensitivity` — 0,25…4; значения вне допустимых пределов приводятся к ним при чтении, файл пишется целиком через временный файл и переименование, сломанный файл читается как «нет файла» и меню открывается с умолчаниями). Меню запоминает и последний выбор (режим, нейроны, бэкенд, WAD, уровень, сложность). Каждое изменение на экране настроек применяется сразу (громкость, режим окна, масштаб интерфейса) и сразу записывается в файл.

**Когда меню не открывается:** с аргументами `--iwad`, `--doom-args` или `--fly` игра стартует сразу, как раньше (скрипты и проверки не меняются); переменная `MYENGINE_DOOM_NO_MENU=1` делает то же самое. Для снимков самого меню: `MYENGINE_DOOM_MENU_SCREEN=play|settings|about` открывает нужный экран сразу, а `MYENGINE_UI_SCRIPT=<файл>` ([rl-ui.md](rl-ui.md)) ведёт меню по расписанию (клавиши, `shot`, `quit`) — так сняты экраны задачи V1.

**В игре с мухой.** Tab показывает мозг мухи на весь экран поверх приглушённой игры и возвращает обратно; справа в панели то же облако в малом виде ([brain-view.md](../flybrain/brain-view.md)). Для снимков без человека Tab задаётся скриптом интерфейса (`<сек> key Tab`) или `MYENGINE_DOOM_KEYS=<кадр игры>:tab`.

**Режимы и контроллеры.** Меню строит строки списка режимов из `DoomGameServices::modes` (тексты режимов — подпись, описание, теги, сигнальный путь — лежат в `DoomMenu.cpp` по `id`, поток отдаёт только `id`, `available`, `reason`, `modeIndex`) (`DoomMode`: `id` — `human`, `fly`, `fly-learn`, `human-vs-fly`, `fly-vs-fly`, `swarm`, `title`, `description`, `available`, `unavailableReason`, `doomArgs`, `make(choice, error)`). Что выбрал игрок, приходит в `make` как `DoomLaunchChoice` (нейроны, бэкенд мозга, уровень, сложность, число мух роя, зерно, а также рендерер и сервис живых видов окна для 3D-мозга в панели). Режим без `make` — человек. Карточка доступна, когда режим доступен в списке приложения (`DoomMode::available`); недоступный показывается серым с причиной (нет коннектома, нет цепи роя). Из меню проверены все пять режимов: Human, Fly plays, Human vs Fly, Fly vs Fly, Swarm.

**Пауза и возврат в лабораторию.** Esc в игре (когда меню самого DOOM закрыто) открывает паузу: игра, мозг и мышь стоят, кадр затемнён на 62 %, а слева ещё темнее, чтобы панель мозга и HUD под ней не читались; огромное `PAUSED`, сверху строка `FLY PLAYS · E1M2 · HURT ME PLENTY` и для режимов мухи `● BRAIN ON GPU | 1.3× REAL TIME` (справа она кончается перед панелью). Пункты: RESUME (Esc тоже возвращает), DOOM MENU (меню DOOM: сохранения, настройки), LABORATORY, EXIT. DOOM (doomgeneric) живёт один раз на процесс, поэтому LABORATORY запускает программу заново (`FlyDoom.exe`; из редактора `myengine.exe --game doom`) сразу на экране PLAY, а это окно закрывает: настройки и последний выбор подхватываются из `settings.json`, облако за меню загружается заново. Esc, нажатый на заставке или в меню самого DOOM, по-прежнему идёт в DOOM. Для проверок без человека Esc и Tab задаются скриптом интерфейса `MYENGINE_UI_SCRIPT` (`<сек> key Esc`, `<сек> key Tab`, см. [rl-ui.md](rl-ui.md)); он же ведёт кнопки паузы. По номеру кадра игры то же делает `MYENGINE_DOOM_KEYS=<кадр>:esc|tab`.

**Ограничения.** Возврат в лабораторию — это перезапуск программы (секунды на загрузку коннектома и облака).

## Кто играет: контроллеры (N1)

Окно FlyDoom (`DoomGameFlow`) умеет отдать игру контроллеру: `engine/include/myengine/game/DoomController.h` (`IDoomController::Advance(game, dt)` вместо `DoomGame::Advance`, `DrawPanel` — панель справа от картинки). `DoomMode` — пункт меню перед игрой («Human plays» без контроллера, остальные создают контроллер). Приложение (`app/src/main.cpp`) собирает список режимов: человек и, если найден файл коннектома, муха (`game/doomfly`, [flydoom-fly.md](flydoom-fly.md)); больше одного режима — меню на цифрах, `--fly` пропускает его. Контроллеру игра даёт `DoomGame::StepTic()`: ровно один такт, что бы ни говорили часы (так мозг шагает игрой такт за тактом). Контроллер может также `HumanPlays()` (клавиатура и мышь играют игроком консоли, как при Human vs Fly) и `Secondary()` (вторая картинка рядом с игровой: глаза другого игрока); подробности — [flydoom-fly.md](flydoom-fly.md), раздел про два игрока (D1b).

## Точки расширения для N1 и D1

Интерфейс заложен сейчас; реализация одного игрока.

- **Команда такта на игрока.** `doom::ITicCmdSource::BuildTicCmd(player, cmd)` вызывается из `G_Ticker` для каждого игрока в игре после того, как DOOM собрал команду из клавиш и мыши (для игрока консоли) или принял её по сети; источник может перезаписать `forwardMove`, `sideMove`, `angleTurn` (в долях 1/65536 круга) и `buttons` (`kButtonAttack`, `kButtonUse`). `DoomGame::SetTicCmdSource(&source)` включает, `nullptr` выключает; `DoomGame::GetTicCmd(player)` читает команду, которую игрок реально получил. Мозг мухи (N1) — это такой источник: нейроны DN дают числа, он собирает из них команду. Тест `hook` показывает, как.
- **Состояние игры для «органов чувств».** `DoomGame::Info()` (такт, уровень, меню, пауза, режим) и `DoomGame::Player(n)` (здоровье, броня, позиция, угол, оружие, убийства) — то, что нужно сетчатке и «боли» (подкрепление) мухи.
- **Вид любого игрока в свой буфер (D1b).** `DoomGame::RenderView(player, ViewBuffer&)`: игрок консоли — то, что DOOM рисует сам (со строкой состояния), любой другой игрок игры — дополнительный проход `R_RenderPlayerView` для `players[n]` (в DOOM экран один, `I_VideoBuffer`: проход подменяет `displayplayer`, палитра и гамма применяются при копировании, ряды строки состояния чёрные). `DoomGame::RenderEyes(player, ViewBuffer&)` делает тот же проход и для игрока консоли (чтобы два мозга видели одинаково). Вызывать между тактами на потоке игры.
- **Несколько игроков в одном процессе (D1b).** Ключ DOOM `-players N` (1…4; наша правка `d_loop.c`, `dg_players` в `doomgeneric.h`): N игроков живут в одной программе без сети (`netgame` ложь, пауза меню работает); игрок консоли — клавиатура или источник команд, остальные получают команды из `ITicCmdSource`. С `-deathmatch` они играют дезматч; `PlayerState::frags`/`deaths`, `DoomGame::RestartLevel()` (уровень заново, все игроки рождаются снова). Ограничение — один DOOM на процесс и одна игра за раз. Тест `players` ниже.
- **Хозяин.** `DoomGame` не знает про окно, DX12 и звук: хозяин ставит `IDoomAudioHost` (звук, музыка) и вызывает `Advance`; поэтому его можно запустить без окна (тесты, обучение мозга быстрее реального времени: `Advance(1.0 / 35)` в цикле без ожидания).

## Раздать друзьям (пакет FlyDoom, D2)

Пакет собирается кнопкой Build & Package в окне Window > Build (игра FlyDoom) или `powershell -ExecutionPolicy Bypass -File tools\package_game.ps1 -Game flydoom`; результат — папка `dist/FlyDoom` и `dist/FlyDoom-<версия>-win64.zip`. Друг распаковывает zip, запускает `FlyDoom.exe` — и играет: в пакете Freedoom, shareware `doom1.wad` (первый эпизод настоящего DOOM; он в `wads/`, игра берёт его раньше Freedoom) и мозг мухи, если файл был на машине сборки. Если у друга DOOM куплен в Steam, игра возьмёт его (полная игра выше shareware), а `FlyDoom.exe --iwad <файл>` выбирает WAD явно. Состав пакета, лицензии (`COPYING`, `SOURCE.txt` с коммитом, `THIRD_PARTY.txt`), проверка на чистой папке и отдельные случаи («нет doom1.wad», «нет мозга») — в [packaging.md](packaging.md), раздел «FlyDoom».

Перед сборкой на машине нужно: `tools/doom/fetch_freedoom.ps1` (скрипт упаковки запустит его сам, если Freedoom нет), shareware `doom1.wad` в `%LOCALAPPDATA%\FlyDoom\wads` (текст лицензии берётся из репозитория: `tools/package_flydoom/doom1.wad.license.txt`) и, для мухи, `assets/flybrain/malecns_v1.fbrain` (`tools/flybrain/fetch_malecns.ps1`). Чего нет, того нет в пакете: скрипт пишет предупреждение, `version.txt` пакета перечисляет файлы, которые в нём есть.
