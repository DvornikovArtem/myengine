# Замеры звука: XAudio2 против Wwise

Цена звука в игре «до» (XAudio2, сборка без `-DMYENGINE_WWISE`) и «после» (Wwise, `-DMYENGINE_WWISE=ON`): одна и та же игра, один и тот же сценарий матча, настоящее звуковое устройство, одна машина, один вечер. Реализации описаны в [docs/engine/audio.md](../../engine/audio.md) и [docs/engine/wwise.md](../../engine/wwise.md); стабильность Wwise - в [stability.md](stability.md).

## Что получилось: два предложения

Звук в игровом потоке дешёвый в обеих реализациях (`AudioSystem::Update` 0.002 мс у XAudio2 и 0.005 мс у Wwise на кадр в 1.5 мс, вызов `PlayEvent` 8.2 и 3.8 мкс), время кадра в пределах шума (медиана 1.52 мс против 1.52 мс). Но Wwise дороже по процессору в целом: процесс за 93 секунды матча тратит на 2.8 секунды CPU больше (91.0 против 88.2 с, +3 %), потому что у Wwise десятки своих потоков и собственный микшер, а в выигрыше он по памяти (рабочий набор на 8 МБ меньше) и по цене вызова `PlayEvent` (в два раза дешевле).

## Условия

| Параметр | Значение |
| --- | --- |
| **Машина** | AMD Ryzen 7 5800H (8 ядер, 16 логических), 15.4 ГБ ОЗУ, NVIDIA GeForce RTX 3060 Laptop GPU; Windows 11 Pro (сборка 26300) |
| **Питание** | от сети (заряд 99 %), схема электропитания Windows «Сбалансированная» (не менялась) |
| **Звуковое устройство** | устройство Windows по умолчанию, настоящее. XAudio2 открыл его как 8 каналов, 48000 Гц (строка `Audio: device default output, 8 channels, 48000 Hz` в логе); Wwise - как «Wwise: the default device» |
| **Громкость** | замеры шли ночью: общая громкость игры `0.03` (около -30 дБ, `game_settings.measure.json`). Голоса Wwise при такой громкости не становятся «виртуальными» (порог проекта около -80 дБ), микшер у обеих сторон работает в полную силу |
| **Код** | ветка `feature/wwise` с задачами W1-W4 на момент замера (коммит `15fc3ca`; в нём Tracy-зоны `Audio::PlayEvent` и `Audio::BackendUpdate` в XAudio2 `AudioSystem.cpp`: только инструментирование, поведение не менялось; те же зоны есть у Wwise) |
| **Сборки** | RelWithDebInfo (Tracy включён только в ней), две папки сборки одной и той же копии исходников: `off` (XAudio2) и `on` (Wwise); обе вне рабочей копии репозитория, в папке `myengine-measure\wwise` рядом с ним. `cmake -S <исходники> -B off` и `cmake -S <исходники> -B on -DMYENGINE_WWISE=ON`, затем `--build --config RelWithDebInfo --target myengine` |
| **Tracy** | клиент 0.14.1 (сабмодуль `external/tracy`), `tracy-capture -f -s 110` и `tracy-csvexport -u` |
| **Окно** | 1280x720, оконный режим, VSync выключен, лимит кадров выключен: кадр считается как можно быстрее, поэтому процессор занят на 100 % одним ядром у обеих сторон (это игровой поток, не звук) |
| **Сцена** | `--game`, матч 2v2 против ботов Pro, игрок ничего не жмёт: боты играют сами. Сценарий [match.script](match.script) (`MYENGINE_UI_SCRIPT`): меню, PLAY, START MATCH, 90 секунд от старта процесса, выход. Матч идёт примерно с 13-й секунды (после загрузки и стартового отсчёта) |
| **Воспроизводимость** | в окне замера обе стороны сделали одинаковое число событий: 190 вызовов `PlayEvent` у каждой (189-190 по прогонам), 3300 шагов физики |
| **Прогрев** | первые 25 секунд (загрузка, меню, стартовый отсчёт матча) отброшены, окно анализа 25-80 с от начала захвата |
| **Прогонов** | 3 без захвата (CPU, память) и 3 с Tracy у каждой стороны; порядок чередуется (off, on, off, on...) |
| **Журнал игры** | рядом с каждым прогоном (в папке сборки): память Wwise при остановке и строки звука |

Что не менялось: код движка и игры, шейдеры, сцены, настройки игры (все прогоны с одним `game_settings.measure.json`), папка пользователя прогона (`APPDATA` и `LOCALAPPDATA` указывают в папку прогона, настройки человека не трогались).

Как читать:

- Звук в игровом потоке занимает от 0.2 % до 0.4 % кадра у обеих реализаций: микширование идёт в потоках самих XAudio2 и Wwise, игровой поток только ставит команды. Wwise в `Update` дороже (0.0057 против 0.0026 мс), потому что `RenderAudio` отдаёт очередь команд своему потоку и забирает завершения событий, а XAudio2 ничего такого не делает; зато `PlayEvent` у Wwise в два раза дешевле (3.8 против 8.2 мкс): XAudio2 в этой реализации выбирает вариант, считает случайные pitch и volume, берёт голос из пула и стартует буфер, у Wwise всё это в проекте.
- Время кадра совпадает с точностью шума: медиана 1.517 и 1.521 мс. Прогоны по отдельности (медиана кадра, мс): off 1.523 / 1.510 / 1.519, on 1.506 / 1.519 / 1.538. У `on` третий прогон медленнее остальных (35 тыс. кадров вместо 36, p95 1.93 против 1.81 мс): это шум машины, а не звука, но он же тянет вверх среднюю по трём. Без него `on` совпадает с `off` по p95 (1.81) и p99 (2.77).
- `Physics::Step` не менялся (код тот же): его совпадение (0.035 и 0.036 мс) говорит, что машина вела себя одинаково.

## Результаты без захвата: CPU и память процесса

Три прогона без Tracy, значения (median, в скобках по прогонам). CPU - `TotalProcessorTime` процесса за весь прогон: игровой поток, потоки звука, рендера, всё.

| Что | off (XAudio2) | on (Wwise) |
| --- | --- | --- |
| CPU процесса за прогон, с (весь процесс, все потоки), ~93 с | 88.2 (87.7, 88.2, 88.4) | 91.0 (91.0, 90.9, 91.9) |
| CPU в окне матча, % одного ядра | 96.6 | 100.0 |
| Рабочий набор: максимум, МБ | 546.3 (545.0, 549.3, 546.3) | 538.0 (532.6, 538.0, 538.3) |
| Рабочий набор: среднее в окне, МБ | 522.5 | 512.2 |
| Private bytes: максимум, МБ | 973.0 | 988.3 |
| Память менеджера Wwise при остановке | - | 11.57 МБ (11.57, 11.57, 11.57) |

- **CPU:** Wwise тратит на 2.8 с больше за 93 с (+3.2 %), в среднем 0.03 ядра. Разброс между прогонами внутри стороны 0.2-0.7 с, поэтому разница настоящая. Это цена его собственных потоков: у процесса на Wwise 49 потоков против 10 у XAudio2 ([threads/](threads/)); самый тяжёлый из добавленных съел за прогон около 6.3 с (по размеру и составу SDK это поток движка Wwise с микшером голосов матча), ещё несколько - от 0.7 до 1.4 с (по составу SDK: рабочие потоки заданий, менеджер банков, поток потоковых файлов, монитор). Имён потоков Windows не отдаёт, так что точнее нельзя. XAudio2 за то же время: один поток около 2.7 с и ещё два около 0.2-0.4 с.
- **Рабочий набор:** у Wwise на 8 МБ меньше (538 против 546 МБ), среднее в окне на 10 МБ. Банки Wwise лежат в памяти как PCM (6 МБ) и считаются менеджером памяти Wwise (11.6 МБ вместе с буферами и пулами); XAudio2-реализация раскодирует все 24 WAV в 16-бит PCM в свой кэш (5.8 МБ) и создаёт 64 голоса XAudio2.
- **Private bytes** выше у Wwise на 15 МБ (988 против 973): вероятно, виртуальная память под стеки 49 потоков и пулы Wwise: в рабочий набор попадает не всё.

## Выводы

1. **Игровой поток.** Цена звука для него ничтожна в обеих реализациях (0.2 % и 0.4 % кадра), и кадр от выбора реализации не меняется в пределах шума машины. Замена XAudio2 на Wwise не замедляет игру на этой сцене.
2. **Процессор целиком.** Wwise дороже примерно на 3 % процессорного времени процесса (0.03 ядра) из-за отдельных потоков и своего микшера. В кадре это не видно (потоки идут на соседних ядрах), на слабом процессоре с 2-4 ядрами могло бы стать заметно. Это честный минус Wwise: платим CPU за возможности (шины, затухания, RTPC, профайлер Authoring), которых у XAudio2-реализации нет.
3. **Память.** Wwise выигрывает по рабочему набору (-8 МБ), проигрывает по виртуальной (+15 МБ); у XAudio2 нет учёта памяти, у Wwise он есть (11.6 МБ).
4. **Стабильность.** Wwise проверен 14 700 событиями, пустыми и обрезанными банками, 20 циклами запуска: [stability.md](stability.md). Один дефект Wwise найден и закрыт: обрезанный банк вешал синхронный `LoadBank` без потока движка.

## Ограничения замеров

- Одна машина, один вечер (с 05:07 до 05:27 по часам машины), 3 прогона на вид замера. Порядок чередовался, дрейфа сравнения «до» и «после» не найдено, но отдельного контроля дрейфа (как в ЛР3: «до» ещё раз в конце) не делалось.
- Игровой поток не ограничен по кадрам (VSync и лимит выключены), поэтому «CPU в % ядра» у обеих сторон около 100 %: считай только «CPU за прогон, с». Микшер Wwise идёт по часам устройства, а не по кадрам: с лимитом кадров (например 60 в секунду) игровой поток простаивал бы, а разница CPU звуковых потоков осталась бы той же.
- Tracy-зоны видят только игровой поток: время потоков самого звука видно по CPU процесса и по таблице потоков (одним прогоном на сторону, потоки без имён).
- Громкость 0.03: микшер не знает, тихо ли в комнате, но драйвер устройства мог бы вести себя иначе при нулевой громкости; поэтому не 0.
- Звук Wwise при замере был без профайлера Authoring (`MYENGINE_WWISE_PROFILER` не задан): с ним добавляется сетевой поток.

## Как повторить

```powershell
# сборки (исходники - копия ветки в стороне от рабочих папок сессий, чтобы их пути не попали в трейсы)
cmake -S <исходники> -B off
# нужен установленный SDK Wwise 2025.1.12.9287: переменная WWISESDK или -DWWISE_SDK_DIR=<...>/SDK (README.md репозитория, раздел Wwise SDK)
cmake -S <исходники> -B on -DMYENGINE_WWISE=ON
cmake --build off --config RelWithDebInfo --parallel 2 --target myengine
cmake --build on  --config RelWithDebInfo --parallel 2 --target myengine

# прогоны (стороны по очереди, по одному прогону за вызов; номера прогонов задаёт -StartRun)
powershell -File run_wwise_bench.ps1 -ExeDir off\app\RelWithDebInfo -OutDir off -Side off -Runs 1 -StartRun 1
powershell -File run_wwise_bench.ps1 -ExeDir on\app\RelWithDebInfo  -OutDir on  -Side on  -Runs 1 -StartRun 1
powershell -File run_wwise_bench.ps1 -ExeDir off\app\RelWithDebInfo -OutDir off -Side off -Runs 1 -StartRun 1 -Tracy
powershell -File run_wwise_bench.ps1 -ExeDir on\app\RelWithDebInfo  -OutDir on  -Side on  -Runs 1 -StartRun 1 -Tracy
python analyze_wwise.py . --window 25 80
```

Все шесть трейсов проверены `tracy-csvexport -u`: в путях исходников нет путей рабочей папки сессии; то же в файлах результатов.
