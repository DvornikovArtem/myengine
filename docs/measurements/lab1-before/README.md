# Лр1. Замеры до job system

Это наш `baseline`, снятый до появления `job system`. Все цифры получены из трейсов в `traces/`.

## Условия

| Параметр | Значение |
|---|---|
| **Конфигурация сборки** | RelWithDebInfo (`TRACY_ENABLE` включён только в ней) |
| **Tracy** | 0.14.1, клиент из сабмодуля, `tracy-capture -f -s 25` |
| **VSync** | выключен (`MYENGINE_VSYNC` не задана) |
| **Сцена** | `assets/scenes/benchmark.json`, 1036 сущностей, из них 1025 с `Rigidbody` |
| **Окно** | `1280x720` |
| **Прогонов** | 3, по 25с каждый, ввод во время записи не трогался |
| **Бинарный кэш** | `*.myemesh` и `*.myetex` удалялись перед каждым прогоном (холодная загрузка) |

Окно анализа физики `5-20с`. Мы сделали так, потому что в первые секунды тела падают и нагрузка нестабильна. Перцентили считаются методом ближайшего ранга по всем вызовам зоны в окне.

## Физика (окно 5-20 с)

Время одного вызова зоны, мс:

| Зона | Медиана (run 1/2/3) | p95 | p99 |
|---|---|---|---|
| `Frame` | 19.36 / 19.62 / 19.32 | 25.92 / 27.43 / 28.27 | 26.76 / 36.54 / 38.32 |
| `Physics::Step` | 6.76 / 6.85 / 6.71 | 7.48 / 8.27 / 8.90 | 7.92 / 10.14 / 10.09 |
| `Physics::NarrowPhaseAndSolve` | 3.94 / 4.01 / 4.06 | 4.40 / 4.93 / 5.38 | 4.69 / 6.07 / 6.04 |
| `Physics::BroadPhase` | 2.38 / 2.40 / 2.24 | 2.86 / 3.04 / 3.02 | 3.08 / 3.51 / 3.55 |
| `Physics::Integrate` | 0.27 / 0.29 / 0.25 | 0.37 / 0.38 / 0.36 | 0.43 / 0.44 / 0.45 |

Шагов физики на кадр: 1.26 / 1.29 / 1.30 (фиксированный шаг 1/60 с).

Итог: шаг физики около 6.8 мс, в кадре 8.6-8.9 мс физики при кадре 19.4 мс, то есть примерно 45% кадра. Внутри шага: narrow-phase с солвером около 59%, broad-phase около 35%, интегрирование около 4%. Вся работа идёт на главном потоке, остальные 15 логических ядер простаивают.

## Загрузка ресурсов (с холодным стартом)

Вся загрузка укладывается в окно 0.86-1.15 с после старта. Суммы по прогонам, мс:

| Зона | Вызовов | run 1 | run 2 | run 3 | Где выполняется |
|---|---|---|---|---|---|
| `LoadTextureCpuAsset` (декод DDS) | 2 | 140.2 | 119.4 | 119.2 | поток пула `std::async` |
| `LoadMeshCpuAsset` (парсинг OBJ) | 11 | 28.0 | 21.0 | 22.6 | поток пула `std::async` |
| `ResourceManager::FinalizeTexture` | 2 | 31.5 | 18.0 | 15.8 | главный поток |
| `ResourceManager::FinalizeMesh` | 11 | 18.1 | 17.1 | 19.1 | главный поток |
| `Dx12RenderAdapter::CreateTexture` | 5 | 37.3 | 22.4 | 20.5 | главный поток |
| `Dx12RenderAdapter::UploadMesh` | 5 | 13.3 | 12.3 | 14.5 | главный поток |
| `Dx12RenderAdapter::WaitForGpu` | 15 | 4.9 | 4.8 | 4.8 | главный поток |

Худшие кадры во время загрузки: 63.3 и 55.3 мс (run 1), 53.2 и 50.2 мс (run 2), 50.9 мс (run 3) - против медианы 19.4 мс. Пик приходится на `PumpAsyncLoads`, внутри него финализация с `CreateTexture` и синхронным `WaitForGpu`.

## Какие проблемы есть

- Загрузка идёт через `std::async`: нет лимита параллелизма, приоритетов и единого шатдауна. В трейсе видно три разных потока пула;
- `PumpAsyncLoads` финализирует всё готовое за один кадр, лимита на кадр нет;
- Аплоад на GPU синхронный: `ExecuteCommandListAndWait` -> `WaitForGpu`;
- Выход с незавершёнными задачами блокируется в деструкторе `std::future`, отмены нет;
- `LoadTexture`, `LoadShader` и `LoadMaterial` вызывают `ScheduleMeshLoad`, из-за чего текстуры, шейдеры и материалы дополнительно уходят на парсинг как меши и падают с `Unsupported mesh format`.

## Структура папки

- `traces/before_1..3.tracy` - трейсы для `Tracy`, каждый содержит и загрузку (первая секунда), и физику;
- `csv/before_1..3_step.csv` - выгрузка зоны `Physics::Step` (`tracy-csvexport -u -f`).

Важно то, что фильтр `-f` у `tracy-csvexport` работает по подстроке. Для зоны `Frame` в выгрузку попадают также `RenderFrame`, `BeginFrame` и `EndFrame`, поэтому строки нужно фильтровать по точному совпадению колонки `name`.
