# Job System: архитектура и план разработки (ЛР1)

## Контекст

**Проект.** `myengine` - учебный игровой движок на `C++17` / `DirectX 12` под Windows, сборка `CMake + MSVC`. Движок - статическая библиотека `engine/`, приложение - `app/`. Профайлер `Tracy 0.14.1` уже подключён (`TRACY_ENABLE` только в `RelWithDebInfo`).

**Что требует ЛР1.**
- `Job system` как подсистема движка, своя реализация;
- Задача №1: асинхронная загрузка ресурсов на `job system` (парсинг в задаче, финализация на главном потоке с лимитом на кадр, `placeholder` до готовности, корректный выход с живыми задачами);
- Задача №2: распараллелить собственную физику `PhysicsSystem`;
- Замеры до/после: `Release`-сборка, прогрев, 3 прогона, медиана + `p95`/`p99`, трейсы `Tracy`;
- Допфичи: свои `fibers` с ожиданием через переключение, `work-stealing deque` Чейза-Лева, выделенный `streaming`-пул, разметка `Tracy`.

**Baseline** снят и лежит в `docs/measurements/lab1-before/`.

## Общая идея

Делаем модель как в `WickedEngine` + ожидание через `fibers` как у `Naughty Dog`:
- Работа описывается **задачами** (функция + данные) без привязки к какому-то потоку;
- Задачи выполняют **воркеры** - потоки, созданные один раз при старте. Главный поток тоже участвует в работе, пока ждёт;
- Завершение группы задач отслеживается **контекстом** - атомарным счётчиком (не `std::future`);
- `Wait` внутри задачи **не блокирует поток**: текущий `fiber` паркуется, воркер берёт следующую задачу. Когда счётчик доходит до нуля, `fiber` возвращается в очередь готовых;
- Загрузка файлов идёт в отдельном **`streaming`-пуле** на обычных потоках: там блокирующий ввод-вывод допустим и не тормозит кадр.

## Структура репо

```
engine/include/myengine/jobs/
    JobSystem.h - публичный API (единственное, что подключают системы движка)
    SmallFunction.h - функция фиксированного размера без аллокаций
engine/src/jobs/
    JobSystem.cpp - пулы, воркеры, планировщик, Wait, shutdown
    JobQueue.h/.cpp - очередь задач (сначала на мьютексе, потом Чейз–Лев)
    Fiber.h/.cpp - обёртка над Win32 fibers и пул fibers
```

Пространство имён пусть везде будет `myengine::jobs`.

## Публичный API (примерный вид)

```cpp
namespace myengine::jobs
{
    enum class Priority
    {
        High, // кадровая работа: физика, системы + воркеры с fibers
        Streaming, // загрузка ресурсов: обычные потоки, можно блокироваться на IO
        Count
    };

    // Счётчик незавершённых задач. Создаётся на стеке вызывающего и должен жить до Wait
    struct Context
    {
        std::atomic<std::uint32_t> counter{0};
        Priority priority = Priority::High;
    };

    struct JobArgs
    {
        std::uint32_t jobIndex; // индекс внутри Dispatch
        std::uint32_t groupId; // номер группы
        std::uint32_t groupIndex; // индекс внутри группы
        bool isFirstJobInGroup;
        bool isLastJobInGroup;
    };

    using JobFunction = SmallFunction<void(JobArgs), 64>;

    void Initialize(std::uint32_t maxWorkerCount = ~0u);
    void Shutdown();

    std::uint32_t GetWorkerCount(Priority priority = Priority::High);

    // Одна задача
    void Execute(Context& context, JobFunction job);

    // jobCount задач, упакованных в группы по groupSize. Группа выполняется одной задачей подряд
    void Dispatch(Context& context, std::uint32_t jobCount, std::uint32_t groupSize, JobFunction job);

    bool IsBusy(const Context& context);

    // Ждёт, пока counter не станет равным 0
    //  - на главном потоке: главный поток сам выполняет задачи, пока ждёт (как в Wicked);
    //  - внутри задачи на воркере: текущий fiber паркуется, воркер берёт другую работу
    void Wait(Context& context);
}
```

Некоторые правила:
- `Context` нельзя уничтожать, пока по нему есть задачи (всегда `Wait` перед выходом из любого скоупа);
- Лямбда в задаче не должна захватывать больше 64 байт (если же больше данных, то нужно захватить указатель на структуру, которая живёт до `Wait`);
- Во время `Wait` нельзя держать мьютекс (`fiber` может продолжиться на другом потоке). В дебаге это проверяется `assert`-ом.

## Потоки и пулы

| Пул | Число потоков | Fibers | Для чего |
|---|---|---|---|
| High | `Число ядер − 1` + главный поток помогает в `Wait` | Да | Физика, системы ECS |
| Streaming | 1-2 | Нет | Чтение и декодирование файлов |

Некоторые правила:
- Потоки создаются в `Initialize` и живут всю сессию;
- Имена потоков для `Tracy`: `Worker 0..N`, `Streaming 0..N`;
- Когда работы нет, воркер засыпает на `condition_variable` и просыпается при постановке задачи (проверка "есть ли работа" и засыпание делаются так, чтобы сигнал не терялся, то есть это проверка под тем же мьютексом, что и `wait`).

## Очереди задач

**Этап 1 (обязательный).** У каждого воркера своя очередь на мьютексе. Задачи, поставленные не с воркера (например, с главного потока), кладутся в общую очередь. Свободный воркер берёт из своей очереди, потом из общей, потом крадёт у соседей (жертва по кругу).

**Этап 2 (допфича).** Своя очередь каждого воркера заменяется на `deque` Чейза-Лева: владелец кладёт и берёт с одного конца без блокировок, остальные крадут с другого конца через `CAS` (`compare-and-swap` - это атомарная операция процессора: "если в ячейке памяти ещё лежит значение X, запиши туда Y; если там уже что-то другое, ничего не делай и скажи об этом"). Общая очередь
остаётся на мьютексе (в `deque` Чейза-Лева класть может только владелец). Интерфейс очереди не меняется, поэтому замена не затрагивает остальной код. При этом важно, что копировать `JobQueue` из `Wicked` нельзя.

Задача хранится в структуре `alignas(64)` (своя кэш-линия, без `false sharing`) с `SmallFunction` внутри. Аллокаций на задачу нет.

## Fibers и ожидание

Реализация на Win32: `ConvertThreadToFiber`, `CreateFiberEx`, `SwitchToFiber`, `DeleteFiber`.

**Устройство:**
- У каждого воркера есть свой "планировщик" - `fiber`, в который превращается поток воркера;
- Пул рабочих `fibers` создаётся заранее (ориентир: 128 штук по 128 КБ стека);
- Цикл воркера: взять задачу -> взять свободный `fiber` -> переключиться на него -> `fiber` выполняет задачи, пока они есть;
- `Wait` внутри задачи: если счётчик не 0, `fiber` регистрируется в списке ожидающих этого контекста и переключается обратно в планировщик (воркер при этом продолжает работать);
- Последняя задача, которая довела счётчик до 0, переносит ожидающие `fibers` в очередь готовых - их подхватит любой воркер.

**Две гонки, которые нужно закрыть:**
1. **Потерянное пробуждение** - между проверкой "счётчик не 0" и регистрацией в списке ожидающих счётчик может обнулиться. **Решение**: проверка и регистрация под одним спинлоком контекста, а обнуление счётчика и разбор списка - под тем же спинлоком.
2. **Fiber ещё не ушёл, а его уже будят** - другой воркер может возобновить `fiber`, который ещё не закончил переключение со своего стека. **Решение**: `fiber` не помечает себя ожидающим сам - это делает следующий `fiber` сразу после переключения (через поле `previous fiber` у потока).

**Главный поток не паркуется вообще**, т.к. он владеет окном, `d3d12` и пампом ресурсов, поэтому должен продолжать выполнение на своём потоке. Его `Wait` работает как в `Wicked`: выполняет задачи, пока счётчик не станет 0.

**Ограничения на код внутри любой задачи:**
- `thread_local` небезопасен после `Wait`, т.к. поток мог смениться. Флаг `/GT` лечит кеширование адреса `TLS` компилятором, но логику всё равно надо писать с этим в голове;
- Не держать мьютекс во время `Wait`;
- `Tracy`: `TRACY_FIBERS` + `TracyFiberEnter` / `TracyFiberLeave` при переключениях, иначе зоны в трейсе перепутаются между потоками.

## Интеграция №1: загрузка ресурсов

**Файлы:** `engine/src/resource/ResourceManager.cpp`, `engine/include/myengine/resource/ResourceManager.h`.

**Как сейчас:** `ScheduleMeshLoad` / `ScheduleTextureLoad` запускают `std::async` и кладут `std::future` в `pendingMeshLoads_` / `pendingTextureLoads_`. `PumpAsyncLoads` (вызывается из `UpdateHotReload` каждый кадр) финализирует всё готовое за один кадр. Финализация - `UploadMesh` / `CreateTexture` с синхронным `WaitForGpu`.

**Как будет:**
1. `Schedule*Load` ставит задачу в пул `Streaming`. Задача вызывает `LoadMeshCpuAsset` / `LoadTextureCpuAsset` и кладёт результат в **очередь готовых** (вектор под мьютексом). `std::future` и `std::async` при этом уходят полностью;
2. У каждой заявки есть номер поколения. При `hot reload` поколение увеличивается и устаревший результат при финализации отбрасывается;
3. `PumpAsyncLoads` забирает из очереди готовых **не больше N ресурсов за кадр** (константа, ориентир 2 или бюджет ~4 мс), остальные ждут следующего кадра;
4. До готовности отдаётся `placeholder` (уже есть: `BuildMeshPlaceholder` / `BuildTexturePlaceholder`);
5. Отмена: у `ResourceManager` флаг `std::atomic<bool> shuttingDown_`. Задача проверяет его до и после тяжёлой работы и при выставленном флаге ничего не публикует. Деструктор выставляет флаг и делает `Wait` по контексту загрузок. Выход с незавершёнными загрузками не падает и не виснет.

**Порядок в `Application`:** `jobs::Initialize()` - до создания `resourceManager_` (`Application::Initialize`). `jobs::Shutdown()` - после `resourceManager_.reset()` (`Application::Shutdown`).

## Интеграция №2: физика

Файл: `engine/src/ecs/systems/PhysicsSystem.cpp`, метод `PhysicsSystem::Update`.

Реестр компонентов - `unordered_map` на каждый тип. Читать из нескольких потоков можно, пока никто не добавляет и не удаляет компоненты. Поэтому сначала **снапшот** в массив на главном потоке, потом `Dispatch` по диапазонам массива.

**Кто что читает и пишет в шаге физики:**

| Фаза | Читает | Пишет | Параллелится? |
|---|---|---|---|
| **`Integrate`** | `Rigidbody`, `Transform` | `Rigidbody.velocity`, `Transform.position` своего тела | Да, тела независимы |
| **`Bounds`** | `Transform`, `Collider` | `AABB`/`OBB` своего тела в массиве `bodies` | Да |
| **`Grid insert` + пары** | `AABB` | Сетка, список пар | Пока последовательно |
| **`Narrow phase` + `solve`** | Оба тела пары | `Transform` и `Rigidbody` тел с `inverseMass > 0`, `isGrounded` | Да, по цветам |
| **События, статистика** | Результаты пар | `EventBus`, `physicsState` | Нет, на главном потоке |

**Шаги реализации:**
1. **Integrate:** снапшот пар (`Transform*`, `Rigidbody*`) в вектор, `Dispatch` по нему. Счётчик `rigidbodyCount` считается суммой по группам (а не например инкрементом общей переменной);
2. **Bounds:** сбор `bodies` остаётся на главном потоке (обход реестра), расчёт `RefreshCollisionBodyBounds` - `Dispatch`. Вставка в сетку и `BuildCandidatePairs` пока последовательные;
3. **Солвер с раскраской:** сейчас пары решаются по очереди, и каждая меняет оба тела (метод Гаусса–Зейделя). Параллельно можно решать только пары, у которых нет общих изменяемых тел. Поэтому пары раскрашиваются жадно: в одном цвете каждое тело с `Rigidbody` встречается не больше одного раза. Статические тела без `Rigidbody` (пол, стены) только читаются и конфликта не создают. Итерация солвера = проход по цветам по очереди, внутри цвета `Dispatch` по парам (`Intersect` + `ResolveCollision`), между цветами `Wait`;
4. **События и статистика:** на первой итерации каждая пара пишет свой результат (было ли столкновение, импульс, точка, нормаль) в свой слот массива. После `Wait` главный поток проходит массив по порядку и публикует события, заполняет `currentCollisionPairs`, `debugVectors` и счётчики. Публикация в `EventBus` из воркеров запрещена;
5. Результат может немного отличаться от последовательного варианта (другой порядок решения пар), но порядок внутри цвета фиксирован, так что прогоны повторяемы.

Зоны `Tracy` из замеров до (`Physics::Step`, `Physics::Integrate`, `Physics::BroadPhase`, `Physics::NarrowPhaseAndSolve`) сохраняем с теми же именами и границами, чтобы цифры были сравнимы.
